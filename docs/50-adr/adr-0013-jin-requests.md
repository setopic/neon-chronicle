# 周の始まりにジンの依頼を1つ示し、果たせば記憶ポイントを上乗せする

- 日付: 2026-10-18
- 状態: stable

## 背景

周の間にすることは、仕事を選んでイベントに答えることだけで、その周の目標が無かった（issue #37）。[DOM-10](../20-domain/dom-10-characters.md)では、仲介屋のジンが主人公に仕事を回すと決めている。ジンが周ごとに依頼を持ってくれば、周ごとの小さな目標になる。

issueでは、依頼の種類、果たしたときの報酬、断れるか・選べるかの3つを決めることにしていた。

## 決定

1. 依頼の種類は、「仕事」（決まった仕事に、決まった時間だけ就く）と「スキル」（決まったスキルを、決まったレベルまで上げる）の2つにする。値は`game/data/requests.json`に置き、MODで足せる。
2. 依頼は1つの周に1つだけ示す。断ることも選ぶこともできない。果たさなくても失うものは無いので、断る操作は置かない。
3. 示す依頼は乱数で選ばない。前の周の終わりのスキルのレベルが示す条件を満たす依頼を並んだ順に集め、周の番号で順に回す。
4. 依頼を果たした周は、周の終わりに得る記憶ポイントの半分（1以上）を上乗せする。
5. 周の始まりに、ジンの台詞で依頼をログに出す。台詞は依頼ごとに書く。体の状態の欄に、依頼の中身と進み具合（果たしたら「果たした」）を出す。
6. 依頼を果たしたら、ログに出す。転生の画面の「記憶ポイント +N」の行に、依頼の上乗せの分を添える。
7. 依頼は、新しいドメインノード[DOM-12](../20-domain/dom-12-jin-requests.md)に書く。

## 理由

依頼の種類を2つにしたのは、どちらも周の間の行動だけで果たせて、運に左右されないからである。イベントの選択肢を選ぶ依頼は、イベントが乱数で起きるので、プレイヤーが何をしても果たせない周がある。稼いだクレジットの額を求める依頼は、永続強化で稼ぎが周ごとに何桁も変わるので、決まった額では早い周に難しすぎ、遅い周に易しすぎる。仕事の時間とスキルのレベルは、周を重ねても意味が変わりにくい。

報酬を記憶ポイントの割合にしたのも、同じ理由である。決まった量にすると、記憶ポイントが増える後の周ほど報酬が小さく見える。半分にしたのは、依頼を果たすかどうかで、永続強化を買える速さがはっきり変わるようにするためである。すべての周で果たし続けても、記憶ポイントの増え方は1.5倍にとどまり、エンディングまでの時間を大きく縮めない。

示す条件を前の周の終わりのスキルのレベルにしたのは、まだ就けない仕事の依頼が出ないようにするためである。周の始まりのスキルのレベルは開始レベルなので、その周に就ける仕事を表さない。前の周で届いたレベルなら、同じくらいの周を過ごせばまた届く。周の番号で順に回すのは、乱数を使わないイベントの決定（[ADR-0004](./adr-0004-event-rules.md)）と体の種類の決定（[ADR-0012](./adr-0012-choose-body-on-rebirth.md)）に合わせたからである。

断れるようにしなかったのは、果たさなくても失うものが無く、断る操作が画面を増やすだけだからである。選べるようにしなかったのは、転生の画面がすでに1280×720の高さいっぱいで、選ぶ欄を置く高さが無いからである。

進み具合を体の状態の欄に出すのは、その周の状態を出している欄だからである。

## 却下した案

| 案 | 却下理由 |
| --- | --- |
| イベントで決まった選択肢を選ぶ依頼 | イベントは乱数で起きるので、果たせない周がある |
| 決まった額のクレジットを稼ぐ依頼 | 稼ぎが周ごとに何桁も変わり、難しさが周によって大きく違う |
| 報酬を決まった量の記憶ポイントにする | 後の周ほど報酬が小さく見える |
| 報酬を永続強化やインプラントにする | 永続強化とインプラントは、記憶ポイントとクレジットで買うものと決まっている。手に入れ方を増やすと、値段の釣り合いを決め直すことになる |
| 依頼を断れるようにする | 果たさなくても失うものが無く、操作が増えるだけである |
| 2つか3つの依頼から選ぶ | 転生の画面に選ぶ欄を置く高さが無い |
| 依頼を乱数で選ぶ | イベントと体の種類で乱数を使わないことにした決定と合わない |

## 影響

DOM-12を足し、依頼の値を`game/data/requests.json`に置く。言語ファイルに、依頼ごとのジンの台詞`request.<id>.offer`を足す。依頼の中身の文は、依頼の種類ごとの`ui.request_job`と`ui.request_skill`で組み立てる。

周の状態に、依頼のidと、依頼を果たしたかを足す。#37より前のセーブの周は、依頼が無いものとして読む。`playthrough.gd`は依頼を狙わずに遊び、果たした依頼の数を出す。

依頼を足すMODは、`requests`に項目を足し、`request.<id>.offer`を言語ファイルに置く。

## 見直しの条件

依頼を選びたいという声が出たら、転生の画面の高さと合わせて選び方を決め直す。依頼の種類を足したくなったら、その種類が運に左右されずに果たせるかを先に確かめる。
