# 開発の流れ

**この文書は、プロジェクトごとに書き換えてよい。** `.gitattributes`の`merge=ours`が守っているので、テンプレートの更新で上書きされない。ここにあるのは既定値であって、破ると動かなくなる規約ではない。動かなくなるものは、`check`とCIが見ている。

## 順番

```
issue ──▶ grill ──▶ 文書（ADR / UC / DOM）──▶ 実装 ──▶ CI ──▶ main
  │         │              │                    │
  問い      決定           残るもの             implemented_by で文書から指す
```

この順番が守っているのは、1つだけである。**決まる前に書き始めない。** 書いてから直すと、ADRが「決めた記録」ではなく、「揺れた記録」になる。

## 1. issueを立てる

問題が見つかったとき、要件が出たとき、今後のTODOができたときは、issueにする。issueの型、閉じるとき、上流に出す導線、Projectへの追加は、[META-07](./issue-pr-flow.md)にある。

issueどうしの関係は、GitHubの関係の欄で付ける。点検や計画のissueから立てたissueは、その子（sub-issue）にする。ほかのissueの答えを待たないと決められないissueには、待つ先をblocked byで付ける。本文に「#147と合わせる」と書くだけでは、着手の順が一覧に出ない。

## 2. grillで詰める

次の4つの場面では、書き始める前に`/grill`を回す。

| いつ | 合図 | 回さないと何が起きるか |
| --- | --- | --- |
| issueを書く前 | 「決めること」が3つ以上ある、または埋められない | 問いのつもりが、解決策の押し付けになる。最初に思いついた案が、唯一の案として扱われる |
| ADRを起こす前 | 却下した案が書けない | ADRが「決めた記録」ではなく、「揺れた記録」になる |
| 実装に着手する前 | ユースケースの「受け入れ条件」が空、または検証できない書き方 | 完成の判定を、実装者が後から決めることになる |
| `schema.py`の語彙・層を変える前 | ノード種別・エッジ種別・層に手を入れようとしている | 全ノードに影響し、取り込む側に移行作業が要る（major）。着手してからでは戻せない |

**「却下した案が書けない」が、最も分かりやすい合図である。** 対案を検討していない決定は、決定ではなく、成り行きである。

終わる条件は、スキルの側にある（`.claude/skills/grill/SKILL.md`）。要点は、frontierが空であること、つまり断りなく仮定したものが1つも無い状態である。

## 3. 決まったことを文書へ移す

移す先と、issueを閉じるときは、[META-07](./issue-pr-flow.md)にある。実装の置き場と`implemented_by`の書き方は、[META-04](./implementation-layout.md)にある。

## 4. 実装する

着手する前と、差分を出す前に、`/lean`を回す。書かずに済む道を、先に探す（[META-06](./principles.md)）。

モジュールの説明の1行目に、ノードのidを書く。`implemented_by`の根拠になる。

識別子は、ドメインの用語表に合わせる。`G013`はコードに届かないので、書くときに合わせる。

文書と実装は、同じコミットに入れる。リポジトリを分けると原理的にできないことで、同居させている理由そのものである（[META-04](./implementation-layout.md)）。

## 5. PRを出すか、mainへ直接出すか

既定では、mainへ直接pushしてよい。単独で開発することを前提にした既定値である。

ただし、PRのときにしか動かない検査が2つある。

| 検査 | 何を見るか | 直接pushだと |
| --- | --- | --- |
| `check --since origin/<base>` | `G015`（追従漏れ）の窓が、baseまで広がる | 未コミットの変更しか見ない。コミットしてしまうと見えなくなる |
| `graph-check.yml`の`refs` | PRの本文が、実在するノードのidを指しているか | 走らない |

だから、次のときはブランチを切ってPRにする。

| PRにするとき |
| --- |
| grillを回した変更（ノードを増やした、決定を変えた） |
| `schema.py`の語彙・層を変えた |
| 複数のノードにまたがる変更 |

それ以外は、mainへ直接pushしてよい。誤字の修正にPRは要らない。**PRを全部に強制すると、上の2つの検査がいつもの儀式になって、読まれなくなる。**

ブランチ名は、ノードのidから取る。`dom-07-cancel-booking`のようにする。どのノードの話かがブランチ名で分かると、`G015`に挙がったときに照合できる。

### PRの粒度

1つのPRに何を入れるかは、[META-07](./issue-pr-flow.md)の「1つのPRには、1つの変更だけを入れる」にある。

## 6. コミットとマージ

コミットの1行目には、何をしたかと、関係するノードのidを書く。実測で、この慣習はすでに成立していた（tournamentで95%、medieval-idleで100%）。

`git add -A`を使わない。同じリポジトリを、別のセッションが触っていることがある。自分が作ったファイルを、名指しで足す。

人間のレビュアーは置いていない。単独開発なので、関門はCIである。複数人になったら`CODEOWNERS`を置き、この節を書き換える。

`--strict`（警告も失敗として扱う）が効くのは、mainへのpushとPRである。PRで落ちなければ、マージした後のmainも落ちない（テンプレート1.22.0）。PRの`--strict`は、`G015`・`G017`では失敗しない（一覧だけを出す）。それ以外のブランチへのpushでは、警告を出すだけにして、書いている途中で止めない。

## リリースと配置

タグは打っていない。版で参照する必要が出ていないからで、必要になったら打つ。打っていないことを既定値として書いておくのは、打ち忘れているのか、打たない方針なのかを、後から区別するためである。

履歴は3つに分かれていて、持ち主が違う（表の4行目は履歴ではなく、配置の手順の行き先である）。

| 何を | どこに書くか |
| --- | --- |
| 検証ツールの層（`graph-doc-template`）の変更 | `TEMPLATE_CHANGELOG.md`と`tools/graph/version.py`（SemVer） |
| 統合型の層（`graph-project-template`）の変更 | `PROJECT_TEMPLATE_CHANGELOG.md` |
| このプロジェクト自身の変更 | `PROJECT_CHANGELOG.md` |
| 配置の手順 | ユースケース（`usecase-runbook`雛形） |

上の2つはテンプレートの層の履歴で、マージで流れてくる。派生プロジェクトが書くのは、`PROJECT_CHANGELOG.md`だけである。

配置には、自動と手動の両方がある。CIから送るもの（GASへの`clasp`など）と、手順書に沿って人が送るもの（ホストへの配置など）がある。どちらも、文書があることが条件である。手順が文書に無い配置は行わない。

## 見積もりと実績

開発はClaude Codeで進め、ClaudeのProプランの使用量の上限が作業量の上限になる。そのため、issueの見積もりは時間ではなく、トークン消費の「コスト指数」で書く。コスト指数は、`~/.claude/token-log/token_log.py`が1ターンごとに記録している相対値で、Haikuの入力1,000トークンを1とする。

GitHub Projectの欄は次の6つである。日付はどれも日本時間で書く。

| 欄 | 書くもの | いつ書くか |
| --- | --- | --- |
| 見積もり | そのissueを閉じるまでのコスト指数 | issueを立てたとき |
| 開始日・期日 | 下の「1週間で使える量」から詰めた予定 | 見積もりを書いたとき |
| 着手日 | そのissueを閉じるPRを最初に作った日 | issueを閉じたとき |
| 終了日 | issueを閉じた日 | issueを閉じたとき |
| 実績 | 実際に使ったコスト指数 | issueを閉じたとき |

見積もり・着手日・終了日・実績は、人もClaudeもProjectに手で書かない。`.github/workflows/project-record.yml`が書く。クラウドのセッションはProjectを読み書きできないので、この形にした。

PRの本文には、閉じるissueを`Closes #番号`と書く。ワークフローは、この行でPRとissueを結び付けて、日付と実績を出す。この行が無いと、PRをマージしたあとにissueを手で閉じても、実績は空のまま残る。

日付は、issueを「完了」で閉じたときに、ワークフローがGitHubの記録から決める。着手日は、本文に`Closes #番号`を持つPRのうち、いちばん早く作られたものの日付である。そのようなPRが無ければ、終了日と同じ日にする。スレッドを始めてからPRを作るまでに日をまたいだときは、着手日が実際より遅く出る。

実績も、issueを閉じたときにワークフローが決める。そのissueを閉じるPRのコミットから`Cost-Index:`の行を拾い、セッションごとの最大値を足したものである。行の書き方と出し方は、下の「実績の出し方」にある。Claudeは実績を計算しない。

見積もりは、issueを立てたClaudeがコメントで付ける。1行目が`見積もり:`か`実績:`で始まる持ち主のコメントを、ワークフローが拾ってProjectの同じ名前の欄に写す。`実績:`のコメントは、ワークフローの出した値を手で直すときに使う。値は数字で書き、「小」のような大きさの名前では書かない。見積もりはissueの本文には書かない。Projectの欄と二重になるからである。

issueを立てる作業にかかった分は、その作業を生んだissueの実績にする。点検の結果をissueに分けたなら、その点検のissueに付ける。そのようなissueが無いときは、マイルストーンごとに「計画」のissueを1つ作り、そこに付ける。こうすると、振り返りで計画にかかった分を別に見られ、個々のissueの見積もりと実績の比にも混ざらない。

```text
見積もり: 5,000
```

issueを閉じたスレッドのClaudeは、次の形のコメントを付ける。実績を直すときは、閉じた後に`実績:`のコメントを付ける。後から付けたコメントの値で上書きされる。

```text
日程に響いたこと: なし
```

ワークフローは、変数`PROJECT_URL`と秘密`ADD_TO_PROJECT_PAT`の両方があるときだけ動く。設定の仕方は、ワークフローの冒頭にある。

「日程に響いたこと」には、作業を延ばしたり縮めたりした出来事を1行で書く。分類は、下の振り返りで使う4つ（着手の遅れ・作業量の見誤り・範囲の変更・待ち）から選び、具体的なことを添える。無ければ「なし」と書く。この欄は、閉じたときにしか正確に書けない。振り返りの時点では、スレッドを読み返さないと分からなくなっている。

見積もりの目安は、このプロジェクトで閉じたissueの実績から取る。2026-10-18の振り返りで下の値に直し、2026-10-19の振り返りでは据え置いた（理由は節の最後にある）。

| 大きさ | 見積もり | 例 |
| --- | --- | --- |
| 小 | 0.5万 | CIの設定、1つの機能の小さな追加 |
| 中 | 0.7万 | 文書と実装をまたぐ機能1つ |
| 大 | 1万 | 設計文書を何本も起こす、仕組みを新しく作る |

1週間で使える量は、仮に20万とする。2026-10-17にProプランの週の上限を16%使っていたとき、手元の記録では6.3万だった。ここから週の上限を約40万と見て、その半分をこのプロジェクトに当てた。クラウドのセッションの消費は手元の記録に入らないので、40万は少なめに出ている。

開始日と期日は、1日に使える量（1週間で使える量の7分の1、約2.8万）まで、同じ日に並べて置く。1日で終わる見込みのissueを、1日に1件ずつ置かない。

### 実績の出し方

同時に進めるissueは1つにし、issueごとにセッションを分ける。セッションの消費は、そのセッションの記録（`~/.claude/projects/*/*.jsonl`）にある。クラウドのコンテナにも手元のPCにも、同じ形で残る。応答ごとに、モデルとトークン数が入っている。

この記録から、`.claude/hooks/cost_index.py`がコスト指数を出す。リポジトリの`.claude/settings.json`が、セッションの開始時にこのスクリプトを回す。スクリプトは記録のパスを`.git/claude-sessions/`に残し、gitの`core.hooksPath`を`.githooks`に向ける。以後のコミットでは、`.githooks/prepare-commit-msg`が、そのセッションのここまでの累計を次の行としてコミットメッセージに足す。セッションを始めたのとは別のクローンでコミットするときは、そのクローンでも`git config core.hooksPath .githooks`を一度実行しておく。セッションの開始時に向け直すのは、セッションを始めたフォルダのクローンだけだからである。

```text
Cost-Index: 5800 (session a75dd425-d13e-5e2c-9216-e5485903f6de)
```

issueが閉じると、ワークフローは閉じたPRのコミットからこの行を拾う。値は累計なので、セッションごとに最大の値を取り、セッションどうしを足す。1つのissueを、クラウドと手元の両方で進めても、同じ形で足される。

コスト指数は、`token_log.py`と同じ重みで出す。各欄に次の重みを掛けて足し、モデルの重み（OpusとFableが5、Sonnetが3、Haikuが1）を掛けて、1,000で割る。

| 記録の`usage`の欄 | 重み |
| --- | --- |
| `input_tokens` | 1 |
| `cache_creation`の`ephemeral_1h_input_tokens` | 2 |
| `cache_creation`の`ephemeral_5m_input_tokens` | 1.25 |
| `cache_read_input_tokens` | 0.1 |
| `output_tokens` | 5 |

5分のキャッシュの重みは、APIの料金の比から取った。`cache_creation`の内訳が無い記録は、すべて1時間のものとして数える。`token_log.py`の重みを変えたら、この表とスクリプトも合わせる。

2026-10-19に、#58のスレッドで、この出し方とセッションの`modelUsage`を比べた。Opusのトークン数は4つの欄とも一致した。`modelUsage`にはHaikuの分（コスト指数で3ほど）もあったが、記録には無かった。セッションの裏で使われる小さな呼び出しと見ている。

この出し方には、数えられない消費がある。

| 消費 | 理由 |
| --- | --- |
| PRの最後のコミットより後の消費 | 行は、コミットの時点の累計だから |
| コミットしなかったセッション | 行が残らない。Projectを触るだけの手元のセッションなどが当たる |
| プロジェクトのチャットを受け持つClaude | issueのPRにコミットしない |
| コンテナが作り直される前の消費 | 作り直したときに記録が引き継がれるかは、確かめていない |

数えられなかった分を足したいときは、`実績:`のコメントで直す。手元の`token_log.py`は、週の消費を見るのに使う。実績のためには回さなくてよい。

### 使用率の記録

週の上限は、使用率（%）でしか分からない。そこで、コミットのたびに、その時点の使用率をコスト指数と並べて残す。

リポジトリの`.claude/settings.json`は、ステータスラインにも`cost_index.py`を当てている。ProとMaxのプランでは、Claude Codeがステータスラインのスクリプトに、5時間と週の使用率を渡す。スクリプトはその値を画面の下に出し、`.git/claude-sessions/usage.json`に残す。コミットのとき、残した値が10分以内のものなら、`prepare-commit-msg`が`Cost-Index:`の行の次に`Usage:`の行を足す。

```text
Cost-Index: 5800 (session a75dd425-d13e-5e2c-9216-e5485903f6de)
Usage: 5h 23% (resets 2026-10-19T17:50+09:00), 7d 41% (resets 2026-10-24T09:00+09:00)
```

`resets`は、その枠が区切られる日時（日本時間）である。7dの`resets`が同じ行どうしは、同じ週の中の値である。

`Usage:`の行が付くのは、ターミナルで起動した`claude`のセッションのコミットだけである。2026-10-19に手元で確かめたところ、デスクトップアプリのセッションではステータスラインが回らず、値が残らなかった。クラウドのセッションでも回らない。手元で自分のステータスラインを設定していても、このリポジトリの中ではこちらが使われる。

### 振り返りの仕方

マイルストーンを閉じたら、見積もりと実績の比を出し、目安の表と「1週間で使える量」を直す。直した値と理由は、この節に書く。

同じときに、日程のずれも振り返る。Projectの欄は、手元のRemote Controlのセッションで`gh api graphql`を使って読む。手元の`gh project item-list`は、日本語の欄の名前が文字化けして値を読めなかった。issueごとに、着手のずれ（着手日と開始日の差）と、期間のずれ（着手日から終了日までの日数と、開始日から期日までの日数の差）を出す。ずれの理由は、実績のコメントの「日程に響いたこと」から取り、次の4つに分けて件数を数える。

| 分類 | 例 | 多いときに直すもの |
| --- | --- | --- |
| 着手の遅れ | 前のissueが長引いた、順番を入れ替えた | issueの順番と、日程の詰め方 |
| 作業量の見誤り | 見積もりより大きかった、小さかった | 目安の表 |
| 範囲の変更 | 途中で決まったことが増えた、減った | issueの切り方（grillで詰め切れていたか） |
| 待ち | 人の確認や判断、外のサービスを待った | 「1週間で使える量」と、作業に当てる時間の割合 |

週の上限は、使用率の記録から測り直す。持ち主に使用率を聞かなくてよい。ただし、手元の作業はデスクトップアプリで進めているので、`Usage:`の行はほとんど残らない。そこで、振り返りを始める前に、持ち主が手元のフォルダでターミナルを開いて`claude`を起動し、1回やり取りする。これで、`.git/claude-sessions/usage.json`にその時点の値が残る。振り返りのClaudeは、このファイルを手元のフォルダから読む。

`usage.json`の`at`は値を残した時刻で、`seven_day`の`resets_at`は週が区切られる時刻である（どちらもUnix時間）。週の始まりは、`resets_at`の7日前にあたる。週の始まりから`at`までの消費は、その間にmainへ入ったコミットの`Cost-Index:`の行から出す。値は累計なので、セッションごとに最大の値を取り、セッションどうしを足す。

```bash
git log origin/main --since=<週の始まり> --until=<at> --format=%B | grep '^Cost-Index:'
```

週の上限は、この消費を`seven_day`の`used_percentage`で割って100を掛けた値である。同じ週の`Usage:`の行が2つあれば、2つの時点の使用率の差と、その間の消費からも同じように出せる。

この値は、上限を少なめに出す。使用率には、このリポジトリのコミットに残らない消費も入るからである。プロジェクトのチャットを受け持つClaude、ほかのプロジェクト、最後のコミットより後の消費がそれにあたる。

## 機械で強制できないもの

grillを回したかどうかは、CIからは見えない。回した証跡はチャットにしか残らず、ADRに「grillした」と書いても、それが本当かは確かめられない。

だから、上の表は「回さないと何が起きるか」まで書いてある。強制ではなく、代償を先に見せる形にしてある。

同じ理由で、次のものも機械では見ていない。目で見るしかない。

| 見ていないもの | 理由 |
| --- | --- |
| ブランチを切ったか | 直接pushを禁じていない |
| コミットの粒度 | 「文書と実装を同じコミットに」は測れない |
| `10-architecture`の用語 | 依存の向きの都合で、`G013`が届かない |
| 実装の識別子と用語表の一致 | `G013`は、文書の本文だけを見る |
